## Findings

### F1 — [MUST FIX] AC7 Violated: `Results.NotFound()` returns empty body, not RFC 7807 Problem Details

**File:** `backend/src/SiesaAgents.API/Endpoints/ClienteEndpoints.cs:26`

AC7 states: _"Returns `404 Problem Details` when the `id` is not found. **Follows Problem Details RFC 7807 on all errors.**"_

The implementation uses `Results.NotFound()` which returns HTTP 404 with an **empty response body**. `Program.cs` does not configure `builder.Services.AddProblemDetails()` or `app.UseStatusCodePages()`. The `ExceptionHandlingMiddleware` only intercepts thrown exceptions — it does not post-process `IResult` responses from Minimal API handlers.

The integration test `GetClienteById_WhenNotFound_Returns404` only asserts status code, not body shape:
```csharp
Assert.Equal(HttpStatusCode.NotFound, response.StatusCode);  // body not checked
```

This means both the implementation and its test fail to meet AC7's explicit Problem Details requirement.

**Fix:** Change `Results.NotFound()` to `Results.Problem(statusCode: StatusCodes.Status404NotFound, title: "Not Found", detail: "Cliente not found")` — or add `builder.Services.AddProblemDetails()` to `Program.cs` and update the test to assert the Problem Details body.

### F2 — [SHOULD FIX] Unsafe structural cast for error status detection duplicated in two files

**Files:** `backend/src/SiesaAgents.API/` → No, **Frontend:**
- `frontend/src/modules/crm/clientes/application/useCliente.ts:10`
- `frontend/src/modules/crm/clientes/presentation/ClienteDetailView.tsx:24`

Both files use an unsafe inline structural cast to detect HTTP status:
```typescript
// useCliente.ts
const axiosError = error as { response?: { status?: number } }

// ClienteDetailView.tsx
(error as { response?: { status?: number } })?.response?.status === 404
```

This pattern:
- Has no runtime type guard — a non-Axios error (e.g., a thrown `string`) silently passes the cast
- Duplicates the same shape in two files — if the HTTP client ever changes, both must be updated
- Ignores that Axios exports `isAxiosError(error)` + `AxiosError` type for this exact purpose

**Fix:** Use `axios.isAxiosError(error)` or extract a shared `getHttpStatus(error: unknown): number | undefined` utility.

### F3 — [SHOULD FIX] Split-panel layout markup duplicated between route files

**Files:**
- `frontend/src/routes/_app/clientes.tsx:12-26`
- `frontend/src/routes/_app/clientes.$clienteId.tsx:14-30`

Identical markup is copy-pasted across both route files:
```tsx
<div className="flex h-full">
  <div className="w-[280px] flex-shrink-0 border-r border-slate-200 overflow-hidden flex flex-col">
    <ClienteListView ... />
  </div>
  <div className="flex-1 ...">
```

Panel width (`280px`), border color (`border-slate-200`), overflow, and flex classes are defined in two places. Epic 2 has 3 more stories (create/edit/delete) that will likely follow the same split-panel pattern. If the panel width changes from `280px` to `320px`, every route file must be updated.

**Fix:** Extract a `ClientesSplitLayout` wrapper component that accepts the right-panel content as a `children` prop.

### F4 — [LOW] Integration test missing timestamp assertions

**File:** `backend/tests/SiesaAgents.IntegrationTests/Clientes/ClienteEndpointsTests.cs:130-136`

`GetClienteById_WhenExists_Returns200WithShape` validates `Nombre`, `Id`, `Nit` but not `CreatedAt` or `UpdatedAt`:

Assert.Equal("Empresa Detail Test", cliente.Nombre);
Assert.Equal(clienteId, cliente.Id);
Assert.Equal("999-detail-1", cliente.Nit);

**Fix:** Add `Assert.NotEqual(default, cliente.CreatedAt)` and `Assert.NotEqual(default, cliente.UpdatedAt)`.

### F5 — [LOW] `retry: false` in test wrapper has no effect for `useCliente`

**File:** `frontend/src/modules/crm/clientes/application/useCliente.test.ts:23-28`

```typescript
const queryClient = new QueryClient({
  defaultOptions: { queries: { retry: false } },  // ← no effect
})
```

In TanStack Query v5, per-query `retry` options override `QueryClient` defaults. Since `useCliente` defines its own `retry` callback, the wrapper's `retry: false` is silently ignored — the hook's retry logic runs in tests, not the wrapper's setting.

Tests pass because the hook's retry function correctly returns `false` for 404s and network errors, but the `defaultOptions` is misleading: a developer reading the test assumes retries are globally disabled, when actually `useCliente`'s own function governs.

**Fix:** Remove the misleading `retry: false` from the wrapper and add a comment noting that `useCliente` has its own retry logic; or confirm that retry behavior is intentionally tested via the hook.
